## 零之三、用户状态保护：**字节级边界**（不再只靠字段级还原）

审核方第十五轮指出："现有方案把太多责任压在最后还原上。" 认。所以把保护从
**字段级还原**（把 wallpaper/autoOn/styles 逐个写回）升级为**字节级可证明**：

- `tools/state-boundary.mjs` 对两棵数据树（`$DSH_HOME/dsh-bg-atelier`、
  `$DSH_HOME/dsh-bg-atelier-plus`）做指纹快照；**capture / compare / selftest 已内联**：
  开跑前快照 → 收尾核对 → 不干净就按"清理失败"退出（码 6），不允许静默通过。
- **必须跟随目录 junction / 符号链接**（实测踩到：`dsh-bg-atelier\wallpapers` 是
  **Junction → `E:\Download\kuake\wallpapers`**，用户真正的图库在 `DSH_HOME` **之外**；
  第一版跳过链接 ⇒ 只核到 1 个文件却打印"逐字节一致"）。现在跟进去核、用 realpath 防环，
  并把遇到的链接**打印出来**（可见性比"相信它被覆盖了"重要）。
- **判定分类明写**：**用户数据**（`settings.json`、图库）一项都不许变；
  **派生缓存**（`posters/previews/larges/we-stills`）允许新增并单独列出数量
  （出现 removed/changed 仍需留意）。
- **指纹口径 = 全文件 sha256**（不抽样）＋ size/mtime/hash 三者都比，日志写明是
  「内容/大小/修改时间」哪一个变了。⚠️ 这里曾按"≤8MB 记 sha256、更大的只记
  size+mtime+**首尾 64KB**"来"省 IO"：既没省（`readFileSync` 已把整文件读进来）也不准
  —— 审核方用一个「改 9 MiB 文件中段 + 更新时间」的反例证明它漏检（§零之四 反例 3a）。
- **已生效的证据**：真机 `selftest` 与 `compare` 均报
  `✅ 用户数据逐字节一致（settings.json 与图库都没被改动）`；
  顺带证明新的原子写（临时文件 + rename）**没有留下 `.tmp` 垃圾**（留了就会被算成新增文件）。

**进程级隔离已建立**（§零之五）。两者互补：字节级边界证明"验收没动用户数据"，
隔离保证"验收不去碰用户在用的那一套"。

## 零之四、被判据的**独立反例**打过并修掉（可复核）

审核方第十六轮用 **6 个可执行反例**打这套判据，**我独立复跑：6/6 全部复现**

**判据要能被独立反例推翻才算判据；修完之后用同一个反例脚本复跑证明它不再复现。**

| # | 反例 | 根因 | 修法 | 钉住它的测试 |
|---|---|---|---|---|
| 1 | 同进程并发写共用临时文件：A 报成功但磁盘是 B，B 报 ENOENT | 临时名只含 PID | 每次写**独占**临时名（pid+序号+时间+随机）＋**同目标串行提交**；另加 rename 在 Windows EPERM/EBUSY 上的重试 | `verify-host-settings-io.mjs` ⑧a/⑧b/⑧c（40 并发全成功、临时名不同、提交顺序=调用顺序） |
| 2 | PUT `[1,2]` 返回 200，下一次读却判 corrupt | 读/写各写各的校验 | 抽出**唯一**判据 `isSettingsObject`，读写都调；数组/标量一律 400 | ⑦（含"读侧写侧都调它"的源码断言） |
| 3a | 改 9 MiB 文件中段 + 更新时间 ⇒ 仍报 clean | 大文件只比首尾摘要；且 `compareTree` **连 size/mtime 都没比** | **全文件 sha256**（不抽样）＋ size/mtime/hash 三者都比；日志写明是"内容/大小/修改时间"哪个变了 | 审核方脚本 3a + 离线套件 |
| 3b | 改图库里名为 `previews` 的**分类**下的原图 ⇒ 被当缓存 | 缓存分类按"路径里有没有该目录名" | 按**精确根目录 + 相对前缀**分类；图库下一律用户数据 | 同上 |
| 3c | 改 `DSH_BG_ATELIER_SETTINGS_DIR` 指向目录里的设置 ⇒ 不在核对范围 | 写死两棵 `DSH_HOME` 目录 | **照抄 `index.js` 的根目录推导**（含"回退到原插件目录"那条），env 覆盖优先，两侧都核 | 同上 |
| 3d | 让核对树无法枚举（ENOTDIR）⇒ 仍报 clean | `catch { continue }` 跳过 | 枚举/读取失败一律记为错误；**有错误即"核对不完整"，绝不出绿** | 同上 |
| 4 | `capture` 没有收尾边界核对；selftest 的核对在 finally 之外 | 三个分支各写各的收尾 | 抽出 `finalizeAll`：**还原 → 清理 → 边界核对 → 关模拟**四步各自独立、互不阻断 | 真机 capture 路径已见边界核对输出 |

**如实记两件不能算"修好"的事**：
1. 反例 5（并发）在他们脚本里现在**报超时**（`controlled scheduling timeout`）——
   串行化之后"第二个 writeFile 不会与第一个同时开始"，他们的受控调度模型与修复后的并发语义
   不兼容。**我不把这当作"已修好"的证据**，只当我自己写的等价测试（⑧a/⑧b/⑧c）通过。
   他们的脚本要接着跑这条，需按新语义改写（断言"串行且两者都成功"）。
2. `compareTree` 现在把"**只改 mtime、内容与大小都没变**"识别为**原样重写**（信息性，不算失败）——
   首次在真机 capture 路径上见到的正是这种情况（我们的还原把 `settings.json` 按原样写回）。
   这不是放宽判据：hash/size 任一变化仍然判失败（3a 复跑证明）。

**新保护已在真机生效（已复验）**：DSH 重启后，生产只读查询 `GET /bga/settings.json` 返回
**`x-bga-settings-status: ok`**。完整保护链在**隔离实例**上验过（破坏性验证不在生产做）：

### 零之五之二、`run`：一条命令跑完整个隔离验收（**已完成并全绿**）


**根因（抓到证据）**：伴随的报错是 `❌ **用户数据被改动了**` —— 套件的子进程用的是**环境里的真实

## 一、四条固定规则

1. **外观目标固定。** 用明确的参考画面与设置定义"当前目标"；现有基准保留不动。
   新建基准必须记录**原因**与**相对上一份的变化**（写在 manifest 的 `why` 字段与提交信息里）。
2. **覆盖按"插件影响的输出"确定，不按类名。**
   插件会向宿主节点下发颜色/透明度/背景 token（`client.js` 的 `settingsSurfaceCss`、
   `applyTheme` 等）—— 这些宿主节点上的效果**也是覆盖对象**。
   "类名没有 bga 所以不是插件的"这种判断此前已被推翻过一次，不得再用。
3. **每项都必须有正常例和坏例。** 正常情况通过；**故意弄坏后必须失败**。
   比较范围减少、锚点丢失、覆盖不足，一律**报告出来**（非零退出），
   不允许继续宣称"完整一致"。
4. **报告与证据绑定。** 每次验收记录：实际运行版本、浏览器、视口 CSS 宽高、DPR、
   设置快照（字段数 + 关键值）、底图**完整路径**（cat/file）、比较范围（矩形/屏蔽框/
   实际比较像素数）、以及各项结果。**未测项目单列**，不得混在"通过"里。
